# Automation Exercise Playwright Framework

A TypeScript and Playwright framework for running UI and REST API regression tests against the existing [Automation Exercise demo store](https://automationexercise.com). It tests the demo site; it does **not** build, host, or clone an e-commerce website.

For the case-by-case test IDs, actions, expected results, and file mapping, see the [Regression Test Case Catalog](./TEST-CASE-CATALOG.md).

## Technology used

- **TypeScript** for test and framework source code, with strict type checking.
- **Playwright Test** for browser automation, REST API requests, fixtures, assertions, parallel execution, and reporting.
- **Chromium** as the configured browser project.
- **dotenv** to load optional local settings from `.env`.
- **GitHub Actions** to install dependencies and Chromium, type-check, run the regression suite, and upload reports.

The framework uses Playwright's built-in browser and API clients. It does not include an application server or a locally implemented/mock e-commerce backend.

## Requirements

- Node.js 20 or newer
- npm
- Internet access to the demo store

## Setup on Windows

Open PowerShell in the project folder:

```powershell
cd "C:\Users\Bhask\Downloads\Playwright framework"
npm ci
npx playwright install chromium
```

`npm ci` installs the exact dependency versions recorded in `package-lock.json`. Use `npm install` instead if you intentionally need to update dependencies or regenerate the lockfile.

### Configure the target site (optional)

By default, browser and API tests use `https://automationexercise.com`. To use another compatible target, copy the example environment file and edit its values:

```powershell
Copy-Item .env.example .env
notepad .env
```

Set absolute URLs without a trailing path, for example:

```dotenv
BASE_URL=https://automationexercise.com
API_BASE_URL=https://automationexercise.com
```

- `BASE_URL` configures the browser base URL.
- `API_BASE_URL` configures the base URL for API requests. If unset, it falls back to `BASE_URL`.

The configuration validates that both values are absolute URLs. Do not put real payment-card data or production credentials in `.env`; this framework is for the public demo.

Alternatively, set the variables for the current PowerShell session:

```powershell
$env:BASE_URL = "https://automationexercise.com"
$env:API_BASE_URL = "https://automationexercise.com"
npm test
```

## Running tests

Run the complete UI and API regression suite:

```powershell
npm test
```

Run a specific layer:

```powershell
npm run test:ui
npm run test:api
```

Run one test case by its stable ID:

```powershell
npm test -- --grep "AE-UI-002"
npm test -- --grep "AE-API-005"
```

Run a browser visibly, check TypeScript, or open the HTML report:

```powershell
npm run test:headed
npm run typecheck
npm run report
```

`npm run report` opens the report generated by the most recent test run. Playwright writes the HTML report to `playwright-report/`; failure artifacts are written to `test-results/`.

## How the framework is organized

```text
playwright.config.ts              Test discovery, Chromium, timeouts, retries, reports
src/
  api/automationExerciseApi.ts    Typed wrapper around documented account/product REST calls
  fixtures/test.ts                Shared API, account, and page-object fixtures
  pages/                          Page objects for home, login, registration, products, and cart
  types/api.ts                    API response types and response-envelope validation
tests/
  api/                            REST API regression cases
  ui/                             Browser UI regression cases
.github/workflows/playwright.yml  Continuous integration workflow
TEST-CASE-CATALOG.md              Case IDs, setup/actions, expected results, and test mapping
```

### Framework flow

1. **Configuration:** `playwright.config.ts` loads `.env`, validates the site URLs, discovers tests under `tests/`, and configures Chromium, timeouts, parallel workers, retries in CI, and diagnostic reporting.
2. **Test fixtures:** UI cases receive an isolated Playwright `page` plus the shared page objects. API cases receive an API request context pointed at `API_BASE_URL` and the typed `AutomationExerciseApi` wrapper.
3. **Test setup:** Each regression test arranges only the data it needs. Cases that need an account for UI sign-in use the `testAccount` fixture, which creates a unique account through the demo API before the test.
4. **Actions:** UI cases interact with the real website through page objects; API cases call the real demo REST API. Assertions verify the documented behavior and expected UI/API output.
5. **Cleanup:** `testAccount` deletes its account after the test, including when the test fails. UI registration and checkout cases also delete the account they create after successful completion.
6. **Results:** The console and HTML report list each test by its stable case ID. On failure, Playwright retains the trace, screenshot, and video to help diagnose the issue.

Tests are independent and may run in parallel. Do not rely on one case creating state for another; create unique test data in the case or a fixture.

## Regression cases and traceability

Every test title includes a unique ID. The [Regression Test Case Catalog](./TEST-CASE-CATALOG.md) maps those IDs to the feature, preconditions/actions, expected result, and Playwright spec file. For example, `AE-UI-002` is the UI product-search case and can be run on its own with:

```powershell
npm test -- --grep "AE-UI-002"
```

When adding a case, add a test with a new ID, document the same ID and expected result in the catalog, and confirm that the ID selects exactly that test with `--grep`.

## Continuous integration

The [Playwright workflow](./.github/workflows/playwright.yml) runs on pushes, pull requests, and manual dispatch. It checks out the project, sets up Node.js, installs from the lockfile, installs Chromium, runs the TypeScript check and all tests, then uploads the Playwright report and test artifacts.

## Demo limitations

Automation Exercise is a shared practice site, not a production commerce backend. Its documented REST API does not expose cart, coupon, payment, order placement, or order-history endpoints. Cart and checkout can be exercised in the UI, but the UI payment form is a mock flow using fictional card data; no real payment is processed. Coupon and order-management REST regression tests are therefore not claimed as covered. The complete current case list and uncovered capabilities are in the [Regression Test Case Catalog](./TEST-CASE-CATALOG.md).
